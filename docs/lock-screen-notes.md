# 锁屏识别与开机解锁(HOME 解法)

本文记录 **boot unlock** 的判断依据:重启后 Horizon 会停在锁屏界面,不按键最终会休眠并
断网;sys-agent 在开机后如何**只看画面**判断"当前是不是锁屏、是哪种锁屏",以及为什么
按键选 HOME。规则、阈值与测试素材都在本文;命令用法见 `commands.md` 的
"Boot unlock" 一节。

## 锁屏的四种外观

开发机上抓到的实机截图(深浅两套主题 × "开始/继续"两种文案;开启 Screen Lock 时还会出现
第三种"按同一按键3次解锁"):

|界面|左侧三分之一|右侧中间|按键|
|---|---|---|---|
|锁屏("A 开始"/"A 继续",浅色或深色)|游戏新闻面板(有图,杂乱)|一整片单色(浅色约 #E9E9E9,深色约 #2E2E2E),中间只有房子圆环、底部只有提示文字|按一次 HOME 解锁|
|"按同一按键3次解锁"(Screen Lock 开启后出现)|**也是单色**(整屏一块)|同上|同一按键连按 3 次,**间隔约 1 秒以内**,否则计数重来|
|主菜单|图标/新闻|游戏图标、渐变,杂乱|——|
|"由谁来玩软件?"对话框|单色|对话框 + 头像,颜色多|——|

## 判据(只用亮度、不用 OCR)

capssc 返回的是 **baseline JPEG**,所以不需要完整解码:只解每个 8×8 块的 **DC 系数**就得
到"块平均亮度"的小图(1280×720 → 160×90),`jpeg_dc.c` 就做这一件事。`screen_classify.c`
在这张小图上取两块区域(比例是相对的,与分辨率无关):

```
右区:x 0.42~0.97, y 0.15~0.80    (避开状态栏与底部提示条)
左区:x 0.02~0.27, y 0.15~0.80    (普通锁屏那里是新闻面板)
```

每区按 8×5 网格切块,算每块的均值与标准差:

- **平整块** = 标准差 < 8(0~255 亮度);
- **锁屏** = 右区平整块比例 ≥ 0.65 **且** 这些平整块的亮度跨度 ≤ 24(也就是"只有一种颜色");
- **三按型** = 再满足 左区平整块比例 ≥ 0.65;否则是普通一按型;
- 其余判为 `other`(主菜单、对话框等),**一律不按键**;
- 抓屏失败 = `dark`(屏幕已熄灭;偶尔也会遇到纯黑帧,按同样的 dark 处理);
- 解码失败 = `unknown`,**同样不按键**。

实测分离度(每格 = 右区平整比例 / 平整块颜色跨度 / 左区平整比例):

|画面|数值|判定|
|---|---|---|
|锁屏 浅色"A 开始"|0.80 / 0.0 / 0.17|lock-one|
|锁屏 深色"A 开始"|0.80 / 0.0 / 0.17|lock-one|
|锁屏 浅色"A 继续"|0.80 / 0.0 / 0.17|lock-one|
|锁屏 深色"A 继续"|0.80 / 0.0 / 0.17|lock-one|
|"按同一按键3次解锁" 浅色|0.80 / 0.0 / **1.00**|lock-three|
|"按同一按键3次解锁" 深色|0.80 / 0.0 / **1.00**|lock-three|
|主菜单|0.25 / 0.0 / 0.17|other|
|"由谁来玩软件?"|0.50 / **134** / 0.73|other|

主菜单被"平整比例"挡掉,对话框被"颜色跨度"挡掉,两条条件是互相独立的余量。

## 按键为什么是 HOME

- 两种锁屏上 HOME 都能解锁(屏幕亮着时直接解锁;屏幕黑着时先点亮,再次按下解锁);
- HOME 在主菜单上是无害的空操作,**永远不会像 A 那样启动当前选中的游戏**(实测:A 在主菜
  单会直接进入"由谁来玩软件?");
- 屏幕熄灭时,虚拟手柄的 A 只会点亮屏幕、不产生其他效果,所以"点亮"这一步也交给 HOME。

连按 3 次那一型必须**一次连发完成**:抓屏+分析要 1 秒以上,而它的按键间隔窗口约 1 秒,
中间插一次抓屏就会让计数重来(实测)。因此顺序是:先识别出是这一型,再连发 3 次 HOME
(默认间隔 250 毫秒),然后才重新抓屏验证。

## 循环、上限与记录

worker 在 `main()` 里、所有服务就绪之后启动(不抢在 settle sleep 之前:锁屏要停留数分钟,
不需要抢时间,这样也避免极早期去碰 sm/fs/set:sys)。每一轮:抓屏 → 分类 → 动作 → 再看一次。
上限:`maxRounds`(默认 8)与 `deadlineMs`(默认 90 秒);唤醒屏幕最多 `wakeAttempts`
(默认 4)次;发现 Application 在跑立即收手(不取消游戏启动)。结束时删除请求文件,把
`bootUnlock` 报告同样的摘要追加到 `sdmc:/config/sys-agent/boot-unlock.log`,即使网络没起
也能拔卡查看。

## 测试素材与主机回归

`tests/fixtures/` 里的 5 张图由实机截图缩到 480×270 得到(区域判据是相对比例,缩放不影响
结论):`lock-one-light/dark.jpg`、`lock-three-light/dark.jpg`、`home-menu.jpg`。
`make test` 里的 `screen_classify_test` 用它们验证:两种主题的普通锁屏都判 `lock-one`、
两种主题的三按屏都判 `lock-three`(且左区平整)、主菜单判 `other`,并且非 JPEG 数据必须
判 `unknown` 而不是锁屏。解码器本身另外用 Python/PIL 的块均值逐块比对过(14400 块全部
一致,最大差 2)。

## 前提与失效模式(重要)

这套判据是**按当前 Horizon 锁屏的版式量出来的**,不是任何公开接口:

- 锁屏 = 右侧一大片单色;三按型 = 连左侧也是单色;主菜单/对话框 = 明显不平整或多色。
- 将来任天堂改了界面(改版式、加动画、把房子图标挪位、换成纯色兜底画面等),判据就可能
  失效。**失效时的行为是"什么都不按"**(判成 `other`/`unknown`),而不会乱按:报告与日志里
  会看到连续的 `other`/`unknown`,不会看到多余的 HOME。
- 处理方式不是重做设计,而是**重新标定**:跑 `bootUnlock run` 看每一帧的
  `rightFlat/rightSpread/leftFlat`,再把新界面的帧加进 `tests/fixtures/` 并在
  `screen_classify.c` 里调阈值/区域。
